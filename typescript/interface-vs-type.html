两者都能描述对象，但能力并不等价。选择标准不是"哪个更好"，而是"你要用哪个能力"。

只有 type 能做的

1type Status = "a" | "b";                          // 联合
2type Pair = [number, number];                     // 元组
3type IsString<T> = T extends string ? true : false;  // 条件类型
4type Partial2<T> = { [K in keyof T]?: T[K] };     // 映射类型
5type ID = string | number;                        // 原始类型别名
6type Event = `on${string}`;                       // 模板字面量

interface 写不出这些，是语法层面的限制（interface X = "a" | "b" 是语法错误）。

只有 interface 能做的

声明合并是 interface 独有的：

1interface Merged { a: number }
2interface Merged { b: string }      // 自动合并
3
4const merged: Merged = { a: 1, b: "x" };

type 会报 Duplicate identifier：

1type TM = { a: number };
2type TM = { b: string };    // error: Duplicate identifier 'TM'.

这是给第三方库补类型的基础（见 声明合并）。需要合并就必须用 interface。

extends 与 & 的关键差异

两者语义上都是"并且"，但错误检查行为不同：

 1interface Base { a: number }
 2
 3// interface extends：不兼容的覆盖会报错
 4interface Bad extends Base {
 5  a: string;
 6}
 7// error TS2430: Interface 'Bad' incorrectly extends interface 'Base'.
 8//   Types of property 'a' are incompatible.
 9//     Type 'string' is not assignable to type 'number'.
10
11// type 交叉：不报错，但属性类型变成 never
12type BadType = Base & { a: string };
13// a 的类型是 number & string，即 never
& 不会报错，只会静默产生 never

这是 & 的一个陷阱。number & string 是 never，类型检查器不会提示你写错了，只会在后面赋值时以奇怪的方式失败。interface extends 会立刻报 TS2430，错误更早更清楚。

选择标准

用 interface：

  • 描述对象结构（这是最常见的场景）
  • 需要声明合并（给库补类型、扩展全局）
  • 需要 extends 的严格检查

用 type：

  • 联合类型、元组、条件类型、映射类型
  • 给原始类型起别名
  • 组合多个类型（A & B、A | B）
实用规则

默认用 interface，因为它可扩展、可合并、错误检查更严格。需要 type 独有的能力时再换 type。

反过来（默认 type，需要合并时换 interface）也行，但会导致团队里风格不统一。关键是定一个默认值并保持一致。

一个常见误区

interface 不是"只能描述对象"，它也能描述函数和数组：

1interface Fn { (x: number): string }
2interface Arr extends Array<number> {}

反过来 type 也不是"只能描述联合"，它同样能描述对象：

1type Obj = { a: number };

真正的区别只在上面那张能力表里。
